## 1. ISR 实时性优化

### 1.1 SPI 编码器读取超时保护

- **文件**：`user/isr.c:389,424`
- **风险等级**：R2（ISR 逻辑）
- **预估收益**：高 — 防止 ISR 死锁导致整车失控

**当前实现**：
```c
if(AS5047P_OK == as5047p_read_angle_raw(&g_enc_l, &angle_raw_l))
```
SPI 读取没有超时保护。如果 SPI 总线因噪声、虚焊或从设备异常挂起，`as5047p_read_angle_raw` 可能阻塞数毫秒，远超 100μs 的 ISR 截止时限。

**优化方案**：
1. 在 AS5047P 驱动层增加 SPI 传输超时计数器
2. 若单次读取超时，立即返回失败，由 ISR 的编码器故障保持逻辑接替
3. 连续超时超过阈值（如 10 次 = 1ms），触发 SPI 总线复位

**实现难度**：中 — 需要修改 AS5047P 驱动层

### 1.2 浮点除法替换为乘法

- **文件**：`code/foc_svpwm.c:93`
- **风险等级**：R2（ISR 逻辑）
- **预估收益**：中 — 每条除法节省 10-20 个 CPU 周期

**当前实现**：
```c
float omega = d / dt;  // dt = 0.001f (固定值)
```

`dt` 在 1kHz 速度估算中是常量（0.001）。除法指令在 TriCore 上比乘法慢约 3-5 倍。

**优化方案**：
```c
static const float inv_dt = 1.0f / 0.001f;  // = 1000.0f, 编译期计算
float omega = d * inv_dt;
```
或者在 ISR 开头预计算 `inv_dt = 1.0f / dt`（虽然 dt 在本 ISR 中已经固定为 `FOC_CTRL_PERIOD_US * 1e-6f`）。

**实现难度**：低 — 单行修改

### 1.3 速度平均除法的时机

- **文件**：`user/isr.c:492`, `user/isr.c:531`
- **风险等级**：R2（ISR 逻辑）
- **预估收益**：低 — 仅 1kHz 子采样时触发

**当前实现**：
```c
float omega_avg = speed_avg_sum_l / (float)speed_avg_cnt_l;
```
`speed_avg_samples` 配置为 1 时，每次都必须做一次除法。配置为 10 时，每 10 次 1kHz 估算才触发一次除法。影响有限。

**优化方案**：如果 `speed_avg_samples == 1`，直接跳过平均环路，直接使用 `omega_raw` 进行 LP 滤波。当前代码已通过 `speed_avg_cnt_l >= speed_avg_samples` 的逻辑间接处理了此情况。

**实现难度**：低 — 可加快速路径跳过累加器

### 1.5 ISR 执行时间基准测量

- **文件**：`user/isr.c:341,714` (FOC_ISR_TIME_PROFILE), `user/cpu0_main.c:217` (GPIO 初始化)
- **风险等级**：R1
- **预估收益**：中 — 建立性能基线

**当前实现**：P02.6 在 FOC ISR 进入时拉高，退出时拉低。

**建议**：
1. 用示波器记录当前 FOC ISR 脉宽作为基线
2. 分别在空载和满载（PID 活跃 + 编码器正常）情况下测量
3. 如果脉宽超过 80μs（留 20μs 余量），需要排查：
   - SPI 时钟频率是否足够（当前 `AS5047P_SPI_BAUD`）
   - SPI 传输是否有不必要的等待状态
   - SVPWM 计算是否有冗余的浮点转换

**期望基线**：
| 条件 | 预期脉宽 |
|------|---------|
| 编码器正常 + 闭环运行 | 40-60μs |
| 编码器故障（角度保持模式） | 20-30μs |
| 仅速度估算周期（1kHz 子采样） | 50-70μs |

## 2. 双核通信与内存一致性

### 2.1 seq-lock 最大重试保护

- **文件**：`user/isr.c:99-108`
- **风险等级**：R2（ISR 逻辑）
- **预估收益**：中 — 防止极端情况下的无限循环

**当前实现**：
```c
do {
    seq0 = g_foc_runtime_cmd.seq;
    __dsync();
    run_local = g_foc_runtime_cmd.run_enable;
    left_local = g_foc_runtime_cmd.left_target_rpm;
    right_local = g_foc_runtime_cmd.right_target_rpm;
    __dsync();
    seq1 = g_foc_runtime_cmd.seq;
} while (((seq0 & 1u) != 0u) || (seq0 != seq1));
```

如果写端（CPU0 的 `foc_runtime_cmd_publish_isr`）在某次中断中被更高优先级的 ISR 无限期抢占，读端将在此死循环。虽然在当前中断优先级设计下不太可能（CPU0 上 1kHz ISR 优先级 33，无更高优先级 ISR 会抢占它），但作为防御性编程应加上限。

**优化方案**：
```c
uint8_t retry = 0;
do {
    ...
    if (++retry > 100u) {
        // 使用上次成功读取的值，或返回默认值
        break;
    }
} while (...);
```

**实现难度**：低 — 加计数器即可

### 2.2 WiFi 快照双缓冲区

- **文件**：`user/wifi_service.c:243-314`
- **风险等级**：R1（业务逻辑）
- **预估收益**：低 — 当前实现基本足够

**当前实现**：使用 `g_wifi_snapshot_ready` 标志位 + `^1u` 翻转索引。

消费者（`wifi_service_load_latest_snapshot`，wifi_service.c:748）在读取前关闭中断，因此消费者端是安全的。但生产者端（ISR 内）写入后通过 `g_wifi_snapshot_ready = 1u` 发布。如果在写入中途被更高优先级的 CPU0 ISR 抢占且该 ISR 也尝试读取快照，理论上可能读到半成品数据。由于 ISR 优先级控制（1kHz ISR 优先级 33，巡线 31，IMU 30），这种情况不太可能发生。

**优化方案**：如需绝对安全，可增加 seq-lock 风格的序列号验证。当前设计对调试遥测已足够（丢失一帧不影响控制）。

**实现难度**：中 — 增加 seq-lock 需要更多字段

### 2.3 跨核 volatile 变量审计

- **文件**：`user/isr.h`, `user/cpu0_main.c`, `user/isr.c`
- **风险等级**：R2
- **预估收益**：中 — 消除理论上的数据竞争

**现状分析**：

| 变量 | 写入端 | 读取端 | 32位对齐 | 风险 |
|------|--------|--------|---------|------|
| `g_run_enable` (uint8_t) | CPU0 ISR | CPU1 ISR | ✓ | 低 |
| `g_base_speed_rpm` (float) | CPU0 ISR | CPU1 ISR | ✓ | 低 |
| `g_turn_delta_rpm` (float) | CPU0 巡线ISR | CPU0 1kHzISR | ✓ | 低 |
| `g_motor_mech_l_rad` (float) | CPU1 FOC ISR | CPU0 1kHzISR | ✓ | 低 |
| `g_foc_runtime_cmd` (struct) | CPU0 1kHzISR | CPU1 FOC ISR | ✓ | 低(有seq-lock) |

TriCore 架构保证 32 位对齐的单次加载/存储是原子的，因此 float(32位) 和 uint8_t(对 32 位总线的单字节写入也是原子的) 不会出现"撕裂读"。主要风险在于：
- **多变量一致性**：`g_target_left_rpm` 和 `g_target_right_rpm` 可能来自不同的 ISR 迭代
- **编译器重排**：volatile 保证不重排 volatile 访问之间的顺序，但非 volatile 访问可能重排

**优化方案**：
1. 对于需要一致性的多变量组合，使用 seq-lock 封装（当前 FOC 指令已这样做）
2. 在非 seq-lock 路径的跨核读取处添加注释说明"允许读取旧值"（当前多数路径不要求严格一致性）

**实现难度**：低 — 主要是文档和注释

---

### 2.4 `__dsync()` 使用审计

- **文件**：`user/isr.c:78,82,102,106`
- **风险等级**：R2
- **预估收益**：中 — 确保编译器不重排 ISR 关键序列

**当前状态**：仅在 seq-lock 路径中使用 `__dsync()`。这是 `__dsync()` 的正确用法——阻止编译器和 CPU 在 `__dsync()` 两边重排内存访问。

其他跨核变量（如 `g_run_enable`、`g_motor_mech_l_rad` 等）声明为 `volatile` 但未使用 `__dsync()`。这在 TriCore 上通常是安全的，因为：
1. volatile 禁止编译器优化掉或重排对 volatile 变量的访问
2. TriCore 的存储模型是强一致的（TSO-like）

**优化方案**：当前已足够。如果未来启用编译器优化（-O2/-O3），需要在关键序列增加 `__dsync()`。

**实现难度**：不适用（当前已正确）

## 3. 算法与数值稳定性

### 3.1 转弯速度缩放参数语义

- **文件**：`user/isr.c:791-798`
- **风险等级**：R1
- **预估收益**：低 — 可能需要重新标定参数

**当前实现**：
```c
if (turn_speed_scale < 0.0f)  turn_speed_scale = 0.0f;
else if (turn_speed_scale > 0.01f) turn_speed_scale = 0.01f;
```
`turn_speed_scale` 被钳位到 [0, 0.01]，然后作为 `(abs_delta * turn_speed_scale)` 的因子。
- 如果 delta = 500 RPM，scale = 0.01 → 减速 = 5 RPM（几乎为零）
- 这意味着 scale 的取值范围对实际减速效果几乎没有影响

**检查建议**：
1. 确认 `turn_speed_scale` 的原始设计意图是否为 0-100%（即 0-1.0 而非 0-0.01）
2. 如果意图是百分比，钳位范围应为 [0, 1.0]
3. 如果意图是微调参数（0-1%），需要补充文档说明

### 3.2 巡线通道评分除法优化

- **文件**：`user/line_follow.c:280` (`line_follow_calc_channel_score`)
- **风险等级**：R1
- **预估收益**：低 — 16 次除法/帧 × 200Hz = 3200 次/秒，影响有限

**当前实现**：
```c
score = (raw - min) / (max - min);
```
每通道每帧一次浮点除法。16 通道 × 200Hz = 3200 次除法/秒。

**优化方案**：标定时预计算 `inv_range = 1.0f / (max - min)`，运行时：
```c
score = (raw - min) * inv_range;
```
标定更新时重新计算 `inv_range`。

**实现难度**：低 — 修改 `line_follow_calib_update_raw` 增加预计算，评分函数改用乘法

### 3.3 PID 增量式抗饱和（已优化）

- **文件**：`code/foc_svpwm.c:170-188`
- **状态**：✓ 已优化

速度环 PI 使用了带有条件积分钳位的增量式 PID：
- P 项：`kp * (err - err_last)` — 增量式，天然抗微分冲击
- I 项：`ki * err * dt`，积分钳位到 `[-vq_limit, vq_limit]`
- 抗饱和：输出饱和时回退积分器

**可选增强**：
- 积分分离：大误差时关闭积分项（当前 PI 而非 PID，无微分项）
- 变速积分：误差大时减小 ki

### 3.4 NaN/Inf 防护缺口

- **文件**：`user/isr.c:299-716`（FOC ISR 整体）, `code/foc_svpwm.c:76-127`（速度估算）, `code/foc_svpwm.c:403-458`（SVPWM 占空比）
- **风险等级**：R2
- **预估收益**：中 — 防止传感器噪声或 SPI 错误值导致 NaN 传播

**当前状态**：
- `params_sanitize_float()` 使用了 `isfinite()` 检查（params_flash.c:364）
- WiFi 遥测平滑函数使用了 `isfinite()` 守卫（wifi_service.c:382-397）
- **FOC ISR 速度估算和 PI 计算未使用 `isfinite()` 保护**

**风险场景**：
1. SPI 读到错误的编码器值 → 角度跳变 → `d / dt` 产生极大速度值
2. 极大速度值进入 PI → I 项累积到极大值 → `vq` 输出饱和 → 电机剧烈抖动
3. 虽然在编码器失败 150 周期后会停机，但 15ms 内电机可能已经发生危险动作

**优化方案**：
1. 在速度估算结果上增加 `isfinite()` 检查，非正常值丢弃
2. 在 PI 输出上增加饱和检查（已有 `foc_clampf`）
3. 编码器故障恢复后，增加速度估算器的"预热"周期（当前已清零累加器，是好的）

**实现难度**：中 — 需要在多个位置增加检查

---

### 3.5 角度环绕函数的累积精度

- **文件**：`code/foc_svpwm.c:57-74` (`foc_wrap_pm_pi`), `code/foc_svpwm.c:30-43` (`foc_wrap_0_2pi`)
- **风险等级**：R1
- **预估收益**：低 — 长期运行才可能出现

**当前实现**：使用 `fmodf` 做 2π 取模，然后用两个 if 分支做 ±π 环绕。浮点取模在极端值（角度累积到极大值后因为传感器噪声不断累加）会损失精度。

**优化方案**：如果机械角度来源永远是编码器原始值（0-2π），则不存在累积问题。当前角度保持模式（编码器故障时 `mech_hold_l += g_loop_l.omega_m * dt`）可能导致累积。加一个 `foc_wrap_0_2pi` 调用即可。

**实现难度**：低 — 在角度保持路径加一次环绕

## 4. 故障诊断与自愈

### 4.1 失速检测未实现

- **文件**：`user/isr.c:269,655-656,665-666`；`code/foc_svpwm.c:137`（`foc_speed_loop_t.stall_error` 字段）
- **风险等级**：R3（影响电机保护）
- **预估收益**：高 — 防止堵转烧毁电机或 MOSFET

**当前状态**：`stall_error` 字段存在于 `foc_speed_loop_t` 中（foc_svpwm.h:137），在停机路径中被清零（isr.c:655,665），但**从未被设置为 1**。失速检测逻辑是空白的。

**风险**：如果电机被物理卡住（堵转），PI 积分项将持续增长到 `vq_limit`，电机绕组通过最大电流但转子不转，数秒内可能烧毁 MOSFET 或电机。

**优化方案**：
```c
// 在 foc_speed_pi_step() 或 foc_motor_control_step() 中增加：
if (foc_absf(loop->vq_out) >= loop->vq_limit * 0.95f &&
    foc_absf(loop->omega_m) < FOC_STALL_SPEED_THRESHOLD_RADPS)
{
    loop->stall_timer_s += dt;
    if (loop->stall_timer_s > FOC_STALL_TIMEOUT_S)
    {
        loop->stall_error = 1;
    }
}
else
{
    loop->stall_timer_s = 0.0f;
}
```

**实现难度**：中 — 需要增加阈值参数和累加逻辑

### 4.2 编码器故障分级退化

- **文件**：`user/isr.c:411-419`（当前：150 周期后直接停机）
- **风险等级**：R2
- **预估收益**：中 — 让小车在 SPI 短暂故障时缓慢停车而非急刹

**当前实现**：编码器连续失败 `FOC_ENCODER_HOLD_CYCLES`（150 周期 = 15ms）后，`control_angle_ok` 变为 0 → `foc_motor_control_step` 不输出 PWM → 电机自由滑行。

**优化方案**：分 3 级退化：
1. **0-50 周期**（0-5ms）：保持上一角度，全功率输出
2. **50-100 周期**（5-10ms）：保持角度，但线性降低 vq_limit 到 50%
3. **100-150 周期**（10-15ms）：继续降低到 0，停机
4. **150+ 周期**：PWM 关断

当前已有 ramp-down 逻辑（isr.c:262-267）但仅降低 `vq_frac`，不改变控制角度有效性判断。

**实现难度**：中 — 需要修改 `foc_motor_control_step` 的分支逻辑

---

### 4.3 SPI 通信故障后恢复

- **文件**：`user/isr.c:399-408`（编码器恢复后的重置逻辑）
- **风险等级**：R1
- **预估收益**：低 — 偶发 SPI 故障时更快恢复

**当前实现**：编码器恢复后，清零速度累加器并重新开始累积。这导致 1-2 个速度估算周期（1-2ms）的速度值为 0，之后恢复。

**优化方案**：恢复后不立即清零速度累加器，而是将未完成的累加窗口继续使用（如果故障时间 < 1 个速度估算周期）。当前设计已足够保守。

**实现难度**：中 — 收益不大

---

### 4.4 电池电压骤降检测

- **文件**：`user/battery_monitor.c`；`user/isr.c:115-148` (`foc_get_runtime_vbus`)
- **风险等级**：R1
- **预估收益**：中 — 防止电池老化导致比赛中途断电

**当前实现**：电压采样在 200Hz IMU ISR 中每 10 次（50ms）更新一次。`battery_monitor_is_low()` 和 `battery_monitor_is_critical()` 使用静态阈值。

**问题**：大电流加速时，电池内阻导致电压瞬间骤降（如从 8.0V 跌到 6.5V），低于 `min_v` 后 `foc_get_runtime_vbus` 钳位到 `min_v`，但低电标志可能误触发。

**优化方案**：
1. 低电判断增加最小持续时间（如连续 500ms 低于阈值才触发）
2. 增加"电池内阻"在线估算（测空载电压 vs 带载电压的差值）
3. 运行时检测到电压骤降超过某比例（如 15%），降低目标速度而非直接停机

**实现难度**：中 — 需要增加滤波/延迟逻辑

## 5. 存储可靠性

### 5.1 Flash 写入失败无恢复

- **文件**：`user/params_flash.c:659-663`
- **风险等级**：R1
- **预估收益**：中 — 防止参数写入失败导致全部参数丢失

**当前实现**：
```c
if (flash_write_page_from_buffer(PARAMS_FLASH_SECTOR_NUM, PARAMS_FLASH_PAGE_INDEX) != 0u)
{
    // Flash write failed — the page may be in an inconsistent state.
    // Next load will fall back to defaults via magic-number check.
}
```

写入失败后无任何恢复动作。如果 Flash 页被部分写入（部分扇区已擦除、部分未写入），下次加载时 magic number 可能仍然匹配但数据损坏。

**优化方案**：
1. 写入前先设置 magic number 为 0（使页面无效）
2. 写入完成后设置正确的 magic number
3. 失败时：在 IPS200 上显示 "FLASH ERR" 警告用户
4. 考虑使用双页备份策略（A/B 页交替写入）

**实现难度**：高 — 双页策略需要修改 Flash 布局
